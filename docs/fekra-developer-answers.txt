== Rendering & content ==
DQ-07 Next.js version and router
  → App Router
  Notes: Next.js 16.3.0, React 19.2.6, Payload CMS 3.87.1, Tailwind 4.
DQ-08 How is a blog article’s body rendered?
  → Fetched on the server and included in the HTML (SSG/ISR/SSR)
  Notes: Normal (rich-text) articles were always server-rendered. The one article imported as raw HTML (software-outsourcing-in-2026) was shown inside a sandboxed iframe, so its body was missing from the page HTML (FK-06). Pending deploy: it is now rendered into the page HTML (about 2,700 words) with its styling kept.
DQ-09 After an article is published or edited, how does the live page update?
  → On-demand revalidation triggered on save
  Notes: CMS save hooks revalidate the page in all five languages plus the blog list. Pages also refresh on a timer as a fallback (15 min for the blog, 60 min elsewhere).
DQ-10 Where does content live?
  → Headless CMS (Sanity, Payload, Strapi, Contentful…)
  Notes: Payload CMS 3, built into the same Next.js app (admin at /admin), storing data in Supabase Postgres and files in Supabase Storage.
DQ-11 Can Fekra publish and edit articles without a developer?
  → Yes, through an admin interface
  Notes: /admin with drafts, autosave, live preview and one-click translation.
DQ-12 Which fields exist per article? (tick all)
  → SEO title; Meta description; Custom slug; Cover / OG image; Author; Publish date (editable); Updated date; Tags / category; FAQ block; noindex toggle; Canonical override; Draft and preview
  Notes: The slug is shared by all languages. The updated date is set automatically on save. The author is a CMS user. No current article has an author set yet (FK-38).

== Languages ==
DQ-13 Which i18n approach is used?
  → Custom middleware / routing
  Notes: src/proxy.ts. English is unprefixed (/about); other languages are prefixed (/ar/about, /de, /fr, /es); /en/... redirects to the unprefixed URL.
DQ-14 Where is hreflang implemented?
  → Both
  Notes: In every page's <head> and in sitemap.xml. On the live site they currently point at the vercel.app domain; the DQ-06 fix corrects them.
DQ-15 What does x-default point to?
  → English root (/)
DQ-16 Does sitemap.xml list every language URL?
  → Yes, all five languages
  Notes: Each entry carries its language versions as hreflang alternates. Only languages a document is actually published in are listed (the per-document "available locales" setting).
DQ-17 How is the language switcher built?
  → Real <a href> links to the equivalent page
  Notes: The links were only created when the menu was opened, so crawlers could not see them (FK-64). Pending deploy: they are now always in the HTML, just hidden until opened.
DQ-18 What happens when a visitor first arrives at /?
  → Redirects based on browser language
  Notes: Only for the bare homepage "/". A language chosen before (cookie) wins; otherwise the browser language decides (temporary 307). It also remembers the last choice. Search engines send no language preference, so they always get English.
DQ-19 Where are interface strings (menus, buttons) stored?
  → JSON/translation files in the repo
  Notes: src/i18n/dictionaries/{en,ar,de,fr,es}.json.

== Blog translation plan ==
DQ-20 When will blog translation run?
  → Once at publish, stored per language
  Notes: Already built. An editor clicks "Translate" in the article sidebar. All four languages are generated and saved as drafts for review, then published by a person.
DQ-21 Which translation service is planned?
  → An LLM API (OpenAI, Anthropic, Google Gemini…)
  Notes: OpenAI (model set by OPENAI_MODEL, default gpt-5-mini). Please confirm OPENAI_API_KEY is set in Vercel production; I cannot see the production variables.
DQ-22 Will translated articles use translated slugs?
  → Keep the English slug (/ar/blog/english-slug)
DQ-23 Can a person edit a translation after it is generated?
  → Yes, and edits are kept
  Notes: Nothing regenerates on its own. Clicking "Translate" again does overwrite that article's translation drafts.
DQ-24 When the English article is edited, what happens to translations?
  → Nothing
  Notes: Recommend adding an "outdated" flag in a later phase.
DQ-25 Where will the API key be stored?
  → Vercel environment variable, server-side only
  Notes: Translation runs in a CMS endpoint that requires a logged-in editor. The key never reaches the browser.

== Analytics, forms & operations ==
DQ-30 Which tracking tools are installed? (tick all)
  → Google Consent Mode v2
  Notes: GTM, GA4 and the LinkedIn Insight Tag are fully coded (loaded only after cookie consent), but their IDs are empty in CMS → Site settings, so nothing tracks today. Enter the GTM/GA4/LinkedIn IDs there; no code change or deploy needed. Clarity is not installed.
DQ-31 Which conversions are tracked? (tick all)
  → Contact form submitted; Service form submitted; Calendly booking; Job application submitted; Newsletter signup
  Notes: Fired only after a confirmed successful submit. Booking-button clicks are also tracked. Generic CTA clicks and language switches are defined but not fired yet. None of these reach analytics until the IDs in DQ-30 are set.
DQ-32 Where do form submissions go?
  → Both email and Supabase
  Notes: Stored first (Payload CMS → Supabase Postgres, visible in /admin), then emailed through Resend to the addresses in Site settings.
DQ-33 How are CV files stored?
  → Private bucket with expiring links
  Notes: Private applicant-files collection; admins download through short-lived signed links. The public never gets a URL.
DQ-34 Which anti-spam tool protects the forms?
  → Cloudflare Turnstile
  Notes: Also a honeypot field, a minimum fill time, per-IP rate limits and a signed, expiring challenge bound to each form. Verified working in production on 7 Oct.
DQ-35 Dark mode behaviour
  → Remembers the visitor’s choice; No flash of the wrong theme on load
  Notes: Default is light; it does not follow the system setting (deliberate). The logo has a dark-mode version; certification badges have not been checked on dark backgrounds (CHK-02).
DQ-36 What does the floating Fika button do?
  → Links to /fika
  Notes: There is no chat backend. The bubble appears after the cookie choice.
DQ-37 Error monitoring and uptime
  → Vercel logs only
  Notes: There is a /api/health endpoint (checks the app and database) ready for an uptime monitor, but none is configured. No Sentry.
DQ-38 Latest Lighthouse mobile scores for the homepage
  → Lighthouse 12, mobile, one local run against the live homepage on 7 Oct 2026 (the PageSpeed Insights API was over its daily quota): Performance 73, Accessibility 97, Best Practices 96, SEO 100. LCP 5.4 s, FCP 1.9 s, Speed Index 4.7 s, TBT 180 ms, CLS 0. The weak point is LCP (the hero image collage). Re-run in PageSpeed Insights for official numbers.
DQ-39 Anything else Fekra should know (limitations, risks, recommendations)?
  → 1. A release is ready with the 6 Oct audit fixes. Built and checked locally but not yet released: FK-06, 07, 22, 23, 24/27, 29, 30, 33/34, 39, 41/42, 43, 57, 59/60, 63, 64, 66, plus Company/Phone on the contact form (FK-20/21). FK-01–04, 28 and 31/32 are already committed.
2. Three settings only the account owner can change: the production NEXT_PUBLIC_SITE_URL (DQ-06), the tracking IDs in Site settings (DQ-30), and confirming OPENAI_API_KEY (DQ-21).
3. Risk: the developer's local environment points at the production database, so local testing reads (and could change) live content. Recommend a separate staging database/branch in Supabase.
4. CMS saves are slow (articles about 3 s, pages about 9 s) because the database connection pool on Vercel is small. It works, but a Supabase plan with more pooler capacity would help.
5. Adding country, role/stack and team size to the contact form (FK-21) needs new database fields; waiting for Fekra to confirm which fields.
6. Services menu: in batch two the client asked for "Services" to go straight to Hire Dedicated Developers. The audit asks for an overview page instead (FK-23). The overview is built; please confirm that is now the preferred behaviour.
